- 브랜드 한 줄: "물건을 파는 곳이 아니라, 존재가 태어나고 인연을 기다리는 곳."

- 기간: 2026.11.02 착수 → 2027.01.29 홈페이지 교체 배포 (13주)

## 3. 핵심 개념: 탄생기록이 축이다

손님이 리추얼(염색 클래스)에서 만든 작품 하나 = **탄생기록 한 줄**. 이 한 줄에서 A5 카드, 갤러리(SCENES) 카드, 카카오 안내가 모두 나온다.

```
인스타 → 홈 → 예약 → 카카오 확정·하루 전 → 리추얼(현장)
→ 탄생기록 입력 / 고객 업로드 → 대표 승인 → 갤러리 게시 → 카카오 "장면이 걸렸어요" → 재방문
```

- **번호 규칙**: `S-YYMM-NNN` (탄생일 기준 연월, 그 달 안에서 001부터). 예: `S-2611-001`. 한 번 매기면 바뀌지 않고, 삭제해도 번호는 비워 둔다.
- **자동으로 채울 것**: 번호, 탄생일, 그날의 날씨·기온(제주), 예약에서 온 리추얼·지은 이.
- **입력은 폰 우선, 사진 한 장부터**. 손님이 답할 수 있는 항목(나이대·지역·경로·동반 형태)은 태블릿 설문으로 받는다.
- 탄생기록 항목(클라이언트 제안): 최종 염색, 피염물, 옵션, 수령 방법, 현장 결제, 나이대, 지역, 알게 된 경로, 동반 형태, 선호 색, 선호 무늬, 메모. 그리고 설계도 항목: 이름(존재의 이름), 지은 이, 아이템·소재, 그날의 자연, 그날의 한 줄, 사진.

### 상태 흐름

- 예약: `문의 → 대기 → 확정 → 방문` / 확정에서 `노쇼`, `취소`로 갈라짐. 확정 순간 확정 안내, 확정 상태로 전날이 되면 리마인드.
- 네이버 예약은 바로확정이라 **확정 + "새 예약"(확인 전)**으로 들어온다. 대표님이 어드민에서 **확인**하면 그때 카카오 확정 안내·리마인드가 잡힌다. 네이버 예약은 정식 API 대신 **Gmail로 오는 예약 알림 메일 자동 전달**로 받고, 엑셀 올리기는 주 1회 맞춰보기용.
- 탄생기록 게시: `작성 중 → 승인 대기 → 게시` / 동의가 없으면 `비공개`(A5만 출력).

### 리추얼 종류 (11/9 네이버 예약 페이지 기준)

- 상품 5개: 플라워 리추얼 [꽃염색], 그린 리추얼 (나뭇잎 염색), 블루 리추얼 (푸른 풍경), 블루 리추얼 (타이다이), **씬오브유 리추얼** (나만의 풍경 물들이기, 개인 클래스 500,000원 — 이름·가격만 다르고 코스는 같다)
- 가격: 기본 작업비용 70,000원 → 네이버 28% 할인 50,000원(1인). 아이템(30,000~90,000원)은 현장에서 고르고 따로 결제
- 이용 2시간, 만 5세 이상, **바로확정**(예약과 동시에 확정), 이용 1시간 전까지 예약, 네이버페이 결제
- 추가 프로그램: 추가작업(피염물 값만 현장 결제), **풍경한입**(차·디저트, 1인 14,000원, 정가 15,000원), 보물찾기(무료)
- 수령 옵션: 현장픽업(무료), 방문픽업(1인 10,000원, 다음날부터 7일 안), 택배발송(1인 15,000원)
- 안내 언어: 한국어 · English · 日本語 · 中文 (영상·프레젠테이션 중심 다국어 안내)
- 가격·세부는 바뀔 수 있으니 하드코딩하지 말고 데이터로 둔다(`lib/rituals.ts`).

## 5. 데이터 구조 초안

다섯 덩어리로 시작하고, 실제로 쌓이는 걸 보면서 필드를 늘린다.

- **customer** 고객: 이름, 전화번호(국내 기준 키), 이메일(외국인 기준 키), 언어, 카카오 채널 추가 여부, 마케팅 동의
- **reservation** 예약: 날짜·시간, 리추얼, 인원, 옵션(찻자리·수령 방법), 상태, 출처(`naver` · `form` · `manual`), 네이버 예약번호(엑셀 재업로드 시 중복 판단), 메모
- **birth_record** 탄생기록: 번호, 이름, 지은 이, 탄생일, 리추얼, 아이템·소재, 그날의 자연(날씨·기온), 물들인 횟수, 그날의 한 줄, 사진(여러 장, 대표 1장), 게시 동의, 게시 상태, 게시일, 연결된 예약·고객
- **message** 발송: 종류(확정·리마인드·사후·게시), 채널(알림톡·친구톡·이메일·문자), 받는 이, 예약 시각·보낸 시각, 결과(예약됨·성공·실패), 실패 사유
- **inquiry** 문의: 종류(외국인 예약·단체), 이름, 이메일, 원하는 날짜, 인원, 내용, 상태, 확정 시 연결된 예약
- 리추얼은 별도 테이블(ritual)로 둔다. 홈페이지 리추얼 페이지도 이 목록을 쓴다.

관계: customer 1–N reservation, reservation 1–N birth_record, reservation 1–N message, birth_record 1–0..1 message("장면이 걸렸어요"), inquiry 0..1–0..1 reservation

## 6. 외부 연동에서 알고 있어야 할 것

- **네이버 예약**: 사업자용 공개 API가 없다(기획 당시 기준, 실제 계정으로 재확인 필요). 1차 기본은 **스마트플레이스 엑셀 내려받기 → 어드민 업로드**. 같은 네이버 예약번호는 덮어쓰기(갱신). 이후 예약 알림 메일 파싱 자동 등록을 붙일 수 있게 구조를 열어 둔다. 엑셀 열 구성은 클라이언트 샘플을 받아서 맞춘다.
- **카카오**: 알림톡(정보성, 채널 미추가 고객에게도 발송, 사업자 인증·템플릿 심사 필요)으로 예약 확정·리마인드. 광고성·채널 친구 대상 메시지(친구톡 또는 그 후속 상품)로 "장면이 걸렸어요". 발송 대행사·상품 정책은 개발 시점의 최신 문서로 확인한다. 비즈니스 인증 여부가 아직 미확인이라 W5 일정의 전제 조건.
- **외국인 손님**: 네이버·카카오 계정이 없어 예약이 막힌다. 영문 예약 폼 → 어드민 문의함 → 대표가 확정 → 이메일 안내.
- **날씨**: 탄생기록의 그날의 자연(제주 날씨·기온)은 기상청 등 공개 API로 자동.
- **태블릿(공용 기기 4대)**: 기기에 개인정보를 남기지 않는다. 손님이 바뀌면 세션 자동 초기화. 동의 화면에 보관 기간 명시(기간은 미정). 기종(iPad/갤럭시 탭) 미정.

## 7. 디자인 기준

참고: `docs/reference/admin-mood.html` (어드민 무드 시안 3장). **무드만 참고**하고, 서체는 잘 읽히는 것이 우선이다.

> **11/9 조정**: 어드민은 무드 시안을 그대로 따르지 않는다. **흰 바탕에 단출하게**(그레인·큰 가는 숫자·영문 라벨·괄호 라벨 없이) 읽는 속도를 먼저 둔다. 아래 색 중 바탕은 흰색(`#FFFFFF`)으로 바꾸고, 쪽빛·이끼는 리추얼 구분과 주요 액션에만 쓴다. 무드 시안의 결은 고객용 웹·A5 카드에서 살린다. 실제 토큰은 `app/globals.css`.

- **서체: Pretendard 하나만.** 큰 숫자·날짜는 가늘게(250–300), 본문·표·버튼은 400–600. 숫자는 `tabular-nums`. 세리프·명조는 쓰지 않는다. (`docs/reference/fonts/PretendardVariable.woff2`)
- **색 토큰**

| 토큰 | 값 | 쓰임 |
| --- | --- | --- |
| paper (생지) | `#EAE6DE` | 바탕 |
| sheet (종이) | `#F3F0EA` | 카드·패널 |
| sheet-2 | `#E2DDD3` | 보조 면 |
| ink (먹) | `#262521` | 글자·주요 선·주요 버튼 |
| ink-2 / ink-3 | `#5B5850` / `#8F8B82` | 보조 글자 |
| line / line-2 | `#CFC8BB` / `#DDD7CC` | 구분선 |
| jjok (쪽빛) | `#2F4A73` | 포인트 하나, 블루 리추얼, 승인 대기 |
| jjok-soft | `#D9DEE6` | 선택 상태 배경 |
| moss (이끼) | `#767A5F` | 식물 리추얼 |

- **무드 요소**: 생지 같은 종이 바탕(아주 옅은 그레인), 문서 상단의 `No. ____ Date. ____` 기입란, `[ 오늘 ]` 같은 괄호 라벨, 얇은 1px 선, 넓은 여백, 흑백 사진·압화 같은 차분한 이미지.
- **컴포넌트 톤**: 예약은 기록지 한 줄처럼(위아래 얇은 선), 버튼은 둥근 알약형(테두리 먹 / 채움 먹 / 주요 액션 쪽빛), 리추얼 구분은 색 점 하나, 상태는 작은 칩. 카드에 그림자·둥근 모서리를 남발하지 않는다.
- 어드민도 같은 세계관 안에 둔다. 대표님이 매일 보는 화면이 브랜드 바깥에 있으면 피로하다. 다만 읽는 속도가 먼저.

## 8. 말투와 카피

- 해요체, 짧고 담백하게. 천진하고 진심인 톤, 오그라드는 표현은 뺀다.
- 브랜드 가이드 "우리가 지키는 말들": **상품·재고·불량** 대신 **존재·기록·탄생**.
- 메시지 예시
  - 확정: "○○님, 11월 1일 오전 식물 리추얼 예약이 확정됐어요. 아이템은 현장에서 보고 고르시면 돼요."
  - 리마인드: "내일 10시에 뵈어요. 찻자리도 함께 하시면 15,000원이에요."
  - 게시: "○○님의 장면 「오후의 바다」가 SCENES에 걸렸어요."
- 발송 문구는 대표님이 최종 교정한다.

## 9. 기술 메모

- 이 저장소는 Next.js 16 + React 19 + Tailwind v4로 시작했다. **`AGENTS.md`대로 `node_modules/next/dist/docs/`를 먼저 읽고** 코드를 쓴다(학습 데이터와 API가 다르다).
- **11/6 회의에서 확정**: 코드 GitHub → 배포 Vercel → DB Supabase(무료 플랜, 이미지가 많아지면 스토리지 분리 검토). 어드민은 메인 도메인과 분리된 URL로 따로 전달한다. 발송 대행사는 아직 미정.
- 1차 개발 범위(11/6): 네이버 예약 데이터 어드민 확인 → 예약 확인 처리 → 카카오톡 발송. 네이버 API 권한이 막히면 스마트플레이스에서 수동 확인 후 어드민 상태 변경을 트리거로 카카오 발송.
- W2 시안(11/9 주)은 Supabase 연결 전이라 예약을 브라우저(localStorage)에 저장한다. 화면은 `lib/reservations/store.ts`만 쓰므로 그 안쪽만 Supabase로 바꾼다. 로그인도 환경변수 아이디·비밀번호 + 쿠키 하나인 임시 방식(`lib/auth.ts`, `proxy.ts`).
- 어드민 사용자는 1차엔 대표 1명(이후 직원). 권한은 단순하게.
- 화면은 데스크톱 어드민 + 폰(탄생기록 입력) + 태블릿(고객용 웹)을 모두 고려한다.

## 10. 일하는 방식

- 매주 화면 하나: 월 기획·제작 → 3일 안에 초안 공유 → 비동기 피드백 → 주 1회 정기 미팅에서 확정 → 다음 화면.
- 실제 데이터가 아직 적다. 빈 상태도 어색하지 않게, 하나씩 채워 가는 화면으로 만든다. 과하게 많은 정보를 한 화면에 넣지 않는다(기획 단계에서 받은 피드백).
- 데모·시안에는 실명 대신 `김○○` 같은 마스킹 예시 데이터를 쓴다.
